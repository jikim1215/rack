## 1. 시스템 개요 (현재 환경)

```
[사용자 PC] ── HTTPS 443 ──▶ [nginx]  /etc/nginx/conf.d/itam.conf  (TLS 종단 + 프록시)
                                 │  server_name itam.example.go.kr (SNI 분리)
                                 │  HTTP 127.0.0.1:3100
                                 ▼
                     [asset-inventory] systemd (Next standalone, User=asset, 번들 Node)
                                 │
                                 ▼
                     [SQLite] /opt/asset-inventory/data.db  (+ -wal, -shm, WAL 모드)

같은 서버 공존:  공존시스템(share.example.go.kr) = 127.0.0.1:3000 / shared.service / server_name _
                 itam                        = 127.0.0.1:3100 / asset-inventory.service / server_name itam.example.go.kr
                 → nginx가 SNI로 도메인별 분리. 인증서는 공존시스템 것을 공유.
```

### 핵심 경로 / 포트 / 계정 (설치 스크립트 기준 정본)
| 항목 | 값 |
|------|----|
| 앱 디렉터리 | `/opt/asset-inventory` |
| 환경설정 | `/opt/asset-inventory/.env` (권한 600, owner=asset) |
| DB 파일 | `/opt/asset-inventory/data.db` (+ `-wal`, `-shm`) |
| 백업 디렉터리 | `/opt/asset-inventory/backups/` (gzip, 권한 700, 기본 30일 보관) |
| 락 파일 | `/var/lib/asset-inventory/maintenance.lock` (백업/프루닝 상호배제) |
| 번들 Node | `/opt/asset-inventory/node/bin/node` (22.6+ 필수) |
| systemd 유닛 | `/etc/systemd/system/asset-inventory.service` (User=asset, nologin) |
| 앱 포트 | `127.0.0.1:3100` (외부 비노출 — share 3000 과 공존) |
| nginx 설정 | `/etc/nginx/conf.d/itam.conf` (server_name=`itam.example.go.kr`) |
| nginx 포트 | `443`(HTTPS), `80`(→443 리다이렉트) |
| **TLS 인증서** | **공존시스템 공유** `/etc/ssl/certs/shared.crt` + `/etc/ssl/private/shared.key` (`*.example.go.kr`) |
| 접속 도메인 | `itam.example.go.kr` (내부 DNS A레코드 → 서버IP) |
| 서비스 계정 | `asset` (nologin) |
| 초기 관리자 | `admin@example.go.kr` / `admin123` (첫 로그인 후 변경 필수) — 로그인 ID는 이메일 기반(공존시스템 공존 규약) |

> ⚠️ **인증서는 itam 이 만들지 않고 공존시스템(share) 것을 공유**합니다. 갱신은 공존시스템 한 곳에서만 하면 itam 은 자동 반영(nginx reload). `/etc/ssl/certs/shared.crt`·`shared.key`는 **공존시스템 소유이므로 삭제/수정 금지**.

## 2. 관리자 전용 기능 지도

| 기능 | 위치 | 비고 |
|---|---|---|
| 비밀번호 변경(전 사용자) | 설정 → 비밀번호 변경 | 8자+·2종+ 정책 |
| 사용자 생성/역할/팀 배정/비활성/비밀번호 초기화/**접속 허용 IP** | 설정 → 사용자 관리 | 강등·비활성은 다음 요청부터 즉시 반영(token_version) |
| 팀 생성/이름변경 | 설정 → 팀 관리 | 자산 소유의 단일 권위(team_id) |
| 메뉴 권한 매트릭스 | 설정 → 메뉴 권한 | 역할 기본 + 메뉴별 접근/쓰기/승인 세부제한 |
| 로그/감사 조회 | 로그/감사 (총괄 전용) | 접속기록 + 데이터 변경 감사(append-only, 1년 내 삭제 차단) |
| 정리큐(임포트 이상값) 처리 | 대시보드 → 이슈 처리 | 미조치/조치완료/무시 상태 관리 |
| 임포트 배치 되돌리기 | 자산관리 → 일괄등록 결과 | 삭제 예상량 확인 후 실행 |
| 실사 회차 생성/마감/삭제 | 자산실사 | closed 회차는 삭제 불가(증적 보존) |
| 통계 리포트 | 통계 리포트 | 인쇄/PDF 제출용 |

**총괄 전용 API**(방어적 게이트): `/api/users`, `/api/teams`, `/api/audit`, `/api/access-logs`, `/api/admin`.

### 부서(팀)별 데이터 격리 — 인프라 소유 (ADR: 부서 독립 운영)
역할별 가시성: **총괄(admin)=전체**, **전체열람(viewer)=전체 읽기전용(수정·삭제·배치 불가)**, **팀(team)=자기 부서 것만**. 자산/부속/반출입/유지보수/자산실사/통계는 자산의 `team_id` 기준으로 이미 격리되며, 여기에 더해 인프라 5종에 소유(`team_id`)가 도입되었다.

| 메뉴 | 격리 방식 | 팀 계정이 보는 것 |
|---|---|---|
| 랙실장도(racks) · 위치관리(locations) | **하이브리드** | 소유 팀 = 내 팀 **또는** 그 안에 내 팀 자산/리소스가 있으면 노출. 공유 랙(소유 미지정)은 여러 팀이 각자 **자기 자산만** 표시(타팀 U-구간은 이름 없이 회색) |
| IP관리(ip_subnets) · 배선관리(dist_frames) · 계약관리(contracts) | **소유 전용** | 소유 팀 = 내 팀인 것만 |

- **소유 팀 배정**: 각 화면(랙/위치/대역/배선/계약)의 생성·수정 폼에 "소유 팀" 셀렉터가 **총괄에게만** 보인다. 팀 계정이 직접 만든 항목은 **자동으로 자기 팀 소유**가 된다(외부 IDC 등 독립 운영).
- **자산 배치 규칙**: 팀은 **자기 소유 랙 또는 공유(미지정) 랙에만** 자산을 실장할 수 있고, 타팀 전용 랙에는 배치 불가(총괄은 무제한).
- **⚠️ 업그레이드 후 1회 조치**: 기존 데이터는 소유가 비어 있다. **랙/위치**는 파생 규칙으로 자동 노출되지만, **IP대역·배선·계약**은 소유가 지정되기 전까지 **총괄에게만** 보인다 → 총괄이 각 화면 "소유 팀"으로 배정해야 해당 팀에 노출된다. (컬럼 추가 마이그레이션은 앱 기동 시 자동·멱등)

### 사용자별 접속 IP 제어
- 설정 → 사용자 관리의 **허용 IP**에 IPv4/CIDR을 콤마·공백·개행으로 입력.
- **비우면 제한 없음**, 하나라도 있으면 화이트리스트(매칭 규칙 없으면 로그인 거부).
- 프록시 뒤 실IP 식별은 `.env` 의 `TRUST_PROXY=true`(현재 기본 적용)에 의존. 미적용 시 모든 접속이 `direct` 로 수렴해 규칙이 있으면 전부 거부되니 주의.

## 3. 일상 운영 — 서비스 제어 · 헬스체크 · 로그

```bash
# 상태 (셋 다 active 여야 정상 — shared 는 공존시스템)
systemctl status asset-inventory nginx
systemctl is-active shared asset-inventory nginx

# 재시작 (.env·설정 변경 후)
sudo systemctl restart asset-inventory      # 앱만
sudo systemctl restart nginx                # nginx만 (share 세션 유지되는 reload 수준)

# 부팅 자동시작(이미 설정됨)
sudo systemctl enable asset-inventory
```

### 헬스체크 (정상 = 200/302/307)
```bash
IP=<서버IP>
ss -tlnp | grep -E ':3000|:3100|:443'    # share=3000, itam=3100, nginx=443
curl -s -o /dev/null -w 'app  : %{http_code}\n' http://127.0.0.1:3100/login          # 내부 앱
curl -sk --resolve itam.example.go.kr:443:$IP  -o /dev/null -w 'https: %{http_code}\n' https://itam.example.go.kr/login   # 프록시(SNI 필수)
# 두 앱 SNI 분리 확인
curl -sk --resolve itam.example.go.kr:443:$IP  https://itam.example.go.kr/login  | grep -oiE '<title>[^<]*</title>'   # 정보시스템 자산관리
curl -sk --resolve share.example.go.kr:443:$IP https://share.example.go.kr/login | grep -oiE '<title>[^<]*</title>'   # K-Flow
```

### 로그
```bash
journalctl -u asset-inventory -f                       # 앱 실시간
journalctl -u asset-inventory -n 200 --no-pager        # 최근 200줄
journalctl -u asset-inventory -p err -n 50 --no-pager  # 에러만
sudo tail -n 100 /var/log/nginx/error.log              # nginx 에러
sudo grep -i denied /var/log/audit/audit.log | tail    # SELinux 차단(502 추적)
```

## 4. 설정 변경

### 4.1 `.env` 변경
```bash
sudo vi /opt/asset-inventory/.env
sudo chown asset:asset /opt/asset-inventory/.env && sudo chmod 600 /opt/asset-inventory/.env
sudo systemctl restart asset-inventory
```
> `.env` 는 단순 `KEY=VALUE`(셸 문법 금지, 따옴표 없이 그대로). 값 변경 후 반드시 재시작.
> SELinux Enforcing 환경에서 `.env` 를 홈에서 복사해 오면 라벨 문제로 로드가 막힐 수 있음 → `sudo restorecon -R /opt/asset-inventory` 후 재시작.

### 4.2 내부 포트 변경 (3100 이 이미 쓰이는 경우)
설치 시: `sudo NEXT_INTERNAL_PORT=3200 bash asset-inventory/scripts/deploy/setup-nginx.sh`
운영 중 변경: `.env` 의 `PORT=` 수정 → `setup-nginx.sh nginx` 로 nginx upstream 재치환 → 재시작.

### 4.3 서버 IP 변경 / nginx 재구성
```bash
sudo bash /opt/asset-inventory/scripts/deploy/setup-nginx.sh nginx   # IP 자동감지 → conf 재적용 (앱 재설치 없음)
```

### 4.4 TLS 인증서 — 두 가지 운용 모드

인증서는 **nginx(TLS 종단) 계층 전용**이다. Next 앱(127.0.0.1:3100)은 인증서를 보지 않으므로, 인증서 갱신에 **asset 앱 재시작은 절대 필요 없다**(nginx reload만).

**(A) 공유 모드 — 기본(현재)**: itam 이 공존시스템 의 `/etc/ssl/certs/shared.crt`(`*.example.go.kr`)를 그대로 참조.
- 갱신은 공존시스템 한 곳에서만. itam 은 같은 파일 참조라 자동 최신(필요 시 `sudo systemctl reload nginx`).
- ⚠️ `shared.crt`·`shared.key`는 **공존시스템 소유 — 삭제/수정 금지**.

**(B) itam 전용 모드 — 독립 갱신(권장, 공존시스템 무관)**: itam 이 **자체 인증서**(`/etc/ssl/itam/itam.crt`·`itam.key`)를 쓰고, 갱신을 **nginx(itam)에만** 적용한다. 공존시스템 파일·설정과 asset 앱에 영향 없음.

- **최초 1회 전환**(정비창에서): itam 전용 인증서를 배치하고 nginx가 그 경로를 쓰게 한다.
  ```bash
  sudo mkdir -p /etc/ssl/itam
  sudo install -m 644 <새_fullchain.crt> /etc/ssl/itam/itam.crt
  sudo install -m 600 <새_privkey.key>   /etc/ssl/itam/itam.key
  sudo SSL_CRT=/etc/ssl/itam/itam.crt SSL_KEY=/etc/ssl/itam/itam.key \
       bash /opt/asset-inventory/scripts/deploy/setup-nginx.sh nginx
  ```
- **이후 갱신**(반복): 전용 스크립트가 검증→백업→`itam.conf` 인증서 줄만 고정→`nginx -t`→`systemctl reload nginx`(graceful)까지 수행하고, 실패 시 자동 롤백한다. 공존시스템(`shared.*`)와 앱 서비스는 건드리지 않는다.
  ```bash
  sudo bash /opt/asset-inventory/scripts/deploy/renew-cert.sh <새_fullchain.crt> <새_privkey.key>
  ```
- **만료 확인**(모니터링):
  ```bash
  sudo bash /opt/asset-inventory/scripts/deploy/renew-cert.sh check      # itam 전용(B)
  openssl x509 -in /etc/ssl/certs/shared.crt -noout -subject -enddate  # 공유(A)
  ```
- 유효기간이 약 6개월이라 **반기 갱신 대상**. (A)는 공존시스템 캘린더, (B)는 itam 자체 캘린더로 관리.
- 되돌리기(공유 모드 A로 복귀): `sudo SSL_CRT=/etc/ssl/certs/shared.crt SSL_KEY=/etc/ssl/private/shared.key bash /opt/asset-inventory/scripts/deploy/setup-nginx.sh nginx`.

### 4.5 접속 도메인 DNS (유일한 수동 인프라 작업)
폐쇄망은 공인 DNS가 안 통하므로 **기관 내부 DNS에 `itam.example.go.kr → 서버IP` A레코드**(share 와 동일 IP)를 등록해야 도메인 접속이 됩니다.
- **IP 직접 접속은 itam 이 아니라 default(share)로 갑니다.** 사용자에게 반드시 도메인으로 안내.
- 임시 확인은 클라이언트 `hosts` 에 `서버IP itam.example.go.kr` 추가.

## 5. 계정 관리

### 5.1 표준 절차 (UI)
로그인(admin) → **설정 → 사용자 관리**(계정 생성/역할/팀/이메일(ID) 변경/비활성/**삭제**/**비밀번호 초기화**/허용 IP) · **설정 → 메뉴 권한**(역할별 접근/쓰기/승인). 로그인 ID는 **이메일 기반**(공존시스템 와 동일 규약; SSO 없이 계정 규약만 정렬). 시드 기본 계정(`admin@example.go.kr` 등)도 개명·삭제할 수 있으나, **마지막 활성 admin은 강등·비활성·삭제가 차단**되고 **본인 계정은 삭제 불가**(잠금 방지).

**비밀번호 초기화**(설정 → 사용자 관리 → 🔑, 공존시스템 규약과 동일): 초기화하면 해당 계정의 **비밀번호가 그 사용자의 이메일 주소로 설정**되고 강제변경(must_change)이 걸린다. 사용자는 자기 이메일을 알고 있으므로 **전달할 비밀이 없다**(메일 발송·임시비번 노출 불필요). 사용자가 `이메일 / 이메일`(ID=비번=이메일)로 로그인하면 `/change-password` 로 유도되어 **새 비밀번호를 반드시 설정**해야 콘솔에 진입한다. 초기화 시 대상 계정의 기존 세션은 즉시 무효화되고 로그인 잠금도 해제된다.

**메일 릴레이**(설정 → 메일 설정): 폐쇄망 사내 SMTP 릴레이(**허용 IP 방식·무인증** — 계정/비밀번호 없음)를 등록한다. 입력: SMTP 호스트·포트·보안(NONE/STARTTLS/TLS)·발신 주소·발신 이름·기준 URL(메일 링크용)·활성화 토글. 「테스트 메일」로 연결성만 즉시 확인(활성화 토글과 무관). 활성화하면 **비밀번호 초기화 통지** 같은 알림 메일을 발송한다 — **비밀번호 자체는 절대 메일에 담지 않는다**(초기비번=사용자 이메일이므로 담을 비밀도 없음). 릴레이 미설정/발송 실패는 초기화 자체를 막지 않는다(best-effort). 환경변수 `NOTIFICATION_CHANNELS=inapp`(email 미포함) 이면 화면 설정과 무관하게 발송이 강제 차단된다.

### 5.2 관리자 비밀번호 재설정 / 계정 잠금 해제 (비상시)
> 🚫 **`scripts/db-seed.mjs` 를 재설정 용도로 실행하지 마세요.** 이 스크립트는 시작 시 **모든 테이블을 DROP** 하여 **운영 DB 전체가 삭제**됩니다(`--reset-admin` 같은 옵션은 없음). 아래 안전 절차만 사용하세요.

**A. 다른 admin 계정이 있으면** → 설정 → 사용자 관리에서 해당 계정 비밀번호 초기화(가장 안전).

**B. admin 이 유일/전면 잠금이면** — 테이블을 건드리지 않고 해당 계정만 안전하게 재설정:
```bash
cd /opt/asset-inventory
sudo -u asset ./node/bin/node -e '
const crypto=require("crypto");
const Database=require("/opt/asset-inventory/.next/standalone/node_modules/better-sqlite3");
const db=new Database("/opt/asset-inventory/data.db");
const plain="바꿀비번1!";                          // 정책: 8자 이상 + 영문/숫자/특수 2종 이상
const pre=crypto.createHash("sha512").update(plain).digest("hex");   // 저장 규약: scrypt(sha512(평문), salt)
const salt=crypto.randomBytes(32).toString("hex");
const hash=crypto.scryptSync(pre,salt,64,{N:16384,r:8,p:1}).toString("hex");
const r=db.prepare("UPDATE users SET password_hash=?, is_active=1, must_change_password=0, token_version=token_version+1 WHERE username=?").run(salt+":"+hash,"admin@example.go.kr");
db.prepare("DELETE FROM login_attempts WHERE key IN (?,?)").run("u:admin@example.go.kr","ip:direct");
console.log("admin 재설정:", r.changes, "행");
'
sudo systemctl restart asset-inventory
```

**C. 15분 잠금만 즉시 해제**(비밀번호 유지):
```bash
sudo -u asset /opt/asset-inventory/node/bin/node -e '
const D=require("/opt/asset-inventory/.next/standalone/node_modules/better-sqlite3");
const db=new D("/opt/asset-inventory/data.db");
console.log("삭제:", db.prepare("DELETE FROM login_attempts WHERE key LIKE ?").run("u:%").changes, "건 잠금 초기화");
'
```
> 로그인 잠금 키 형식: `u:<사용자명>` / `ip:<IP>`. 5회 실패 시 15분 잠금(계정 키), IP 미식별(`ip:direct`) 시 IP 키 임계치는 4배 완화.

## 6. 백업 · 복구

- 자동 백업: `asset-backup.timer` (**매일 02:00**) → `/opt/asset-inventory/backups/` 에 `data.db.<날짜>.gz`(권한 600, WAL 안전 online backup), **기본 30일 초과 자동 정리**(`BACKUP_KEEP_DAYS`).
- 자동 보존 프루닝: `asset-retention.timer` (**매일 03:30**) → 감사로그/접속기록 **365일 초과분만** 삭제(1년 내 감사로그는 트리거로 삭제 차단).
- 두 작업은 `maintenance.lock` 으로 상호배제(동시 실행 방지).

```bash
# 수동 백업
sudo bash /opt/asset-inventory/scripts/deploy/backup.sh

# 백업 목록
ls -lh /opt/asset-inventory/backups/

# 복구 리허설 (무중단 검증 — 서비스/실DB 안 건드림)
sudo bash /opt/asset-inventory/scripts/deploy/restore.sh --rehearse /opt/asset-inventory/backups/<파일>.gz

# 실복구 (서비스 중지 → pre-restore 백업 → 복원 → 무결성 검증 → 재기동)
sudo bash /opt/asset-inventory/scripts/deploy/restore.sh /opt/asset-inventory/backups/<파일>.gz

# 무결성 단독 검사
( cd /opt/asset-inventory && ./node/bin/node scripts/deploy/db-verify.mjs /opt/asset-inventory/data.db )

# 타이머 상태
systemctl list-timers 'asset-*'
```
> 실복구는 자동으로 `data.db.pre-restore.<시각>` 백업을 남기고 잔존 `-wal/-shm` 을 제거한 뒤 복원합니다. 복원본 검증 실패 시 서비스는 기동하지 않습니다.

## 8. 긴급 대응

### 증상: 접속 불가 (브라우저 연결 안 됨)
```bash
systemctl status asset-inventory nginx        # 둘 다 active 인지
ss -tlnp | grep -E ':443|:3100'               # 리슨 확인
sudo systemctl restart nginx asset-inventory
```

### 증상: 502 Bad Gateway
```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/login   # 앱 살아있나
sudo setsebool -P httpd_can_network_connect 1                          # SELinux 프록시 허용
sudo systemctl restart asset-inventory nginx
```

### 증상: 로그인 "서버 연결 실패" / 500
```bash
grep -c '^AUTH_SECRET=' /opt/asset-inventory/.env    # 1 이어야 함(없으면 세션발급 실패 → production 기동 거부)
journalctl -u asset-inventory -p err -n 50 --no-pager
```
→ `AUTH_SECRET` 누락/기본값이면 강력한 랜덤값 설정 후 `sudo systemctl restart asset-inventory`.

### 증상: 로그인 "사용자가 없습니다"
→ DB 경로 불일치. `.env` 의 `ASSET_DB_PATH` 가 실제 데이터 DB(`/opt/asset-inventory/data.db`)를 가리키는지 확인.

### 증상: 도메인 접속 시 자료공유(공존시스템) 화면이 뜸
→ IP 직접 접속이거나 DNS 미등록. 내부 DNS `itam.example.go.kr → 서버IP` A레코드 확인. SNI 확인은 §3 헬스체크.

### 증상: 인증서 경고 (브라우저)
→ 공유 인증서(shared.crt) 경로/만료 문제. `openssl x509 -in /etc/ssl/certs/shared.crt -noout -enddate` 확인 → 만료면 공존시스템 쪽 갱신. 경로가 다르면 §4.4 로 재지정.

### 증상: DB 손상 의심 (기동 실패, SQLITE_CORRUPT)
```bash
( cd /opt/asset-inventory && ./node/bin/node scripts/deploy/db-verify.mjs /opt/asset-inventory/data.db )
# 손상 확인 시 최신 백업으로 복구:
sudo bash /opt/asset-inventory/scripts/deploy/restore.sh /opt/asset-inventory/backups/<최신>.gz
```
복구 후 **감사로그 마지막 시각**으로 유실 구간을 파악하고, 해당 구간 변경(반출입/실사 등)을 수기 재입력.

### 증상: better-sqlite3 native 로드 오류
```bash
sudo bash /opt/asset-inventory/scripts/deploy/native-planb.sh   # 소스 리빌드(gcc/make/python3 필요)
sudo systemctl restart asset-inventory
```

## 13. 절대 금지 (안전)
- `scripts/db-seed.mjs` 를 운영 DB에 실행 금지 — **모든 테이블 DROP**(전체 삭제). 재설정은 §5.2.
- 공존시스템 자산 수정/삭제 금지: `shared.conf`, `/opt/shared`, `/var/shared`, `shared.service`, **`/etc/ssl/certs/shared.crt`·`shared.key`**(공유 인증서 — itam 이 만든 게 아님).
- itam 설치는 nginx 를 재설치하지 않음(기존 버전 재사용) — 임의로 nginx 를 재설치하지 말 것.
- 정식 운영 중 인증서 경로를 비우지 말 것(자체서명 폴백 → 브라우저 경고).

### itam 만 롤백 (share 무영향)
```bash
sudo systemctl disable --now asset-inventory
sudo rm -f /etc/nginx/conf.d/itam.conf
sudo nginx -t && sudo systemctl reload nginx     # share 그대로, itam 만 제거
# 완전 제거: sudo rm -rf /opt/asset-inventory /var/lib/asset-inventory
#            (shared.crt/key 는 공존시스템 것이므로 절대 삭제 금지)
```
