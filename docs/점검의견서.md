- 문서명: 정보시스템 자산관리 솔루션 점검의견서
- 점검 목적: 현재 소스코드와 산출문서를 기준으로, 실사용 운영 적합성 및 보완 우선순위를 점검하고 개발팀에 전달 가능한 수준의 구체 의견을 제시

## 4. 핵심 결론

### 4.1 총평
현재 시스템은 기능 범위 자체는 충분하다.
- 자산관리
- 랙/위치관리
- 포트맵/토폴로지/IPAM
- 반입/반출
- 유지보수
- 계약관리
- 권한/감사로그

그러나 점검 결과, 현재 상태는 "기능이 잘 정리된 자산관리 솔루션"에 가깝고, 실운영형 ITAM/CMDB 도구로 가기 위해서는 아래 3가지 축을 더 강화해야 한다.

1. 자산 기준정보의 신뢰성
2. 예외/누락/불일치 자산의 식별 가능성
3. 정합성 유지 업무의 자동화 및 AX 활용성

### 4.2 최종 판단
현재 솔루션의 가장 큰 과제는 기능 추가 부족이 아니라 다음이다.

> 자산 현황의 명확성·최신성·정합성을 어떻게 증거 기반으로 유지할 것인가

이 점에서 본 시스템은 방향성은 맞으나, 점검 기준으로 보면 아직 다음 항목이 보완되어야 한다.
- 정합성 규칙의 명문화 부족
- 운영상 우선순위별 액션 정의 부족
- AX 활용 포인트의 구체화 부족
- 공공기관 내부시스템 거버넌스 점검의 깊이 부족

## 6. 화면 및 기능 점검 의견

## 6.1 자산관리 화면
### 판단
가장 중요한 핵심 화면이다.

### 근거
- `src/app/assets/AssetTable.tsx`가 대형 컴포넌트로 집중되어 있음
- 커스텀 필드, 엑셀 업로드, 랙 연결, 이력 조회 등 핵심 기능이 몰려 있음
- 실제 운영자의 주요 업무가 자산 조회/수정/정리라는 점과 일치함

### 점검 의견
현재 자산관리 화면은 기능상으로는 풍부하지만, 점검 관점에서는 아직 "기준대장 통제 화면"으로 완전히 정리되어 있지 않다.

필요한 점검 관점
- 필수정보 누락 자산을 즉시 식별할 수 있는가
- 예외 자산을 필터로 즉시 추릴 수 있는가
- 상태 불일치 자산을 바로 정리할 수 있는가
- 최근 변경 자산과 장기 미갱신 자산을 구분할 수 있는가

### 개발팀 전달용 구체 항목
자산관리 화면은 아래 정리 큐 중심으로 재설계 검토가 필요하다.

1. 정리 대상 기본 큐
- IP 미입력 자산
- OS 미입력 자산
- 관리자 미지정 자산
- 랙 미배치 자산
- 계약 만료 연결 자산

2. 식별 규칙 예시
- IP 미입력: `assets.ip_address` 공란 AND `asset_ips` 미존재
- OS 미입력: `assets.os` 공란
- 관리자 미지정: `assets.admin_name` 공란
- 랙 미배치: `assets.rack_id IS NULL`
- 계약 만료 연계 자산: `contracts.end_date < 현재일` AND `assets.status='active'`

3. 우선순위
- 고효과 / 중노력

### 종합 의견
자산관리 화면은 단순 CRUD가 아니라 "정합성 점검과 정리 작업의 메인 콘솔"로 정의하는 것이 맞다.

## 6.2 대시보드
### 판단
운영 대시보드로서 방향은 좋으나, 현재는 종합 현황판 성격이 강하고, 정리 대상 작업대 성격은 약하다.

### 근거
- `src/app/page.tsx`에 자산 수, 랙 사용률, 포트 사용률, EoS, 보증만료, 데이터 품질, 반입/반출, 유지보수, 계약 만료 등이 분산 표출됨
- 운영 지표는 넓지만, 즉시 조치 대상과 연결되는 구조는 제한적임

### 점검 의견
대시보드는 경영형 대시보드보다 운영형 작업대에 가까워야 한다.

### 개발팀 전달용 구체 항목
대시보드에서 우선적으로 보여줘야 할 항목을 다음처럼 재정의할 필요가 있다.

1. 우선 노출 지표
- 전체 자산 수
- 운영중 자산 수
- 정리 필요 자산 수
- 반입/반출 승인대기 건수
- 계약 만료 연결 자산 수
- 최근 변경 자산 수

2. 정리 필요 자산 정의 예시
- IP 미입력
- OS 미입력
- 관리자 미지정
- 랙 미배치
- 계약 만료 연계

3. 우선순위
- 고효과 / 저~중노력

### 종합 의견
현재 대시보드는 보기 좋은 종합판으로는 적절하나, 실운영 중심으로는 "정리 대상 현황판"으로의 전환 검토가 필요하다.

## 6.3 반입/반출
### 판단
워크플로 범위는 적절하다. 다만 자산현황 최신화 장치로서의 역할이 더 중요하다.

### 근거
- `src/app/movements/MovementsView.tsx`에서 신청/승인/완료/반려 흐름을 관리
- 현재 요구사항도 반입/반출만 승인 필요로 정리됨

### 점검 의견
반입/반출은 이력 관리 기능이 아니라 자산 상태 최신화의 통제 프로세스다.

### 개발팀 전달용 구체 항목
점검 포인트는 다음과 같다.

1. 상태 불일치 룰
- 최신 movement가 `bring_out + completed`인데 자산 상태가 여전히 `active`이면 예외
- 시드 기준 현재 0건이지만, 운영 룰로 상시 점검해야 함

2. 자산 미연결 수기 입력 건 관리
- 현재 `manual` 입력이 가능함
- 실운영에서는 수기 입력 건이 자산대장과 분리되어 누락관리 위험이 생길 수 있음
- 따라서 수기 입력 건을 후속 자산 등록 큐로 연결할 필요가 있음

3. 우선순위
- 중효과 / 중노력

### 종합 의견
반입/반출은 승인 기능 자체보다 자산대장 최신성 보장 수단으로 점검해야 한다.

## 6.4 유지보수 및 계약관리
### 판단
독립 모듈로 유효하나, 자산현황 신뢰성 측면에서 "보조 판단축" 역할을 더 분명히 해야 한다.

### 근거
- 유지보수: `src/app/maintenance/MaintenanceView.tsx`
- 계약관리: README, page 구성, contract_assets 연계 구조 존재
- 데이터 실측 결과: 계약 만료 후 active 자산 4건 존재

### 점검 의견
운영 관점에서는 유지보수/계약 이력 자체보다 아래 식별 기능이 중요하다.
- 계약 만료 연결 자산
- 반복 장애 자산
- 장기 미점검 자산
- 유지보수 중인데 여전히 정상 운영으로 보이는 자산

### 개발팀 전달용 구체 항목
1. 정합성 룰 예시
- 계약 만료 + active 자산 = 예외 관리 큐
- 유지보수 open/in_progress + active 자산 = 경고 큐
- 최근 90일 점검 이력 없음 = 점검 대상 큐

2. 우선순위
- 중~고효과 / 중노력

### 종합 의견
계약/유지보수는 독립 기능이 아니라 자산 운영가능성 판단에 직접 연결되도록 설계 검토가 필요하다.

## 6.5 랙 / 위치관리
### 판단
시각화와 위치 체계는 양호하나, 자산현황 중심 관점에서는 보조 축이다.

### 근거
- `src/app/racks/RackView.tsx`에 충돌/초과 감지 구현 존재
- 실측 결과: 현재 랙 범위초과 0, 랙 충돌 0
- `src/app/locations/LocationManager.tsx`에 위치/랙 관리 구조 존재

### 점검 의견
현재 시드 기준으로는 위치/랙 정합성보다 자산 속성 정합성이 더 시급하다.
즉, 개선 우선순위는 다음과 같이 보는 것이 적절하다.
- 1순위: 자산 속성 정합성
- 2순위: 계약/이력 연계 정합성
- 3순위: 물리배치 시각화 정교화

### 개발팀 전달용 구체 항목
1. 위치관리 검토 포인트
- 위치명 표준화 규칙
- 건물/층/실/랙 명명체계 일관성
- 삭제 시 연관 영향의 사용자 인지성

2. 랙화면 검토 포인트
- 이상 랙만 보기 기능은 유용함
- 다만 전체 사용자 공통 경험의 중심 화면보다는 인프라 담당자용 심화 화면으로 위치시키는 것이 적절함

3. 우선순위
- 중효과 / 중노력

## 7. 공공기관 내부시스템 거버넌스 점검 의견

## 7.1 인증/세션
### 확인 근거
- `src/lib/auth.ts`
- `src/middleware.ts`

### 확인 사항
- 세션 쿠키명: `asset_session`
- 세션 TTL: 24시간
- 세션 서명: HMAC-SHA512
- 패스워드 해시: scrypt + salt
- SameSite: strict
- secure: false (폐쇄망 HTTP 전제 주석 존재)
- 기본 시크릿 미설정 시 경고 로그 출력
- 미들웨어에서 비인가 요청 차단

### 점검 의견

3. HTTPS 전환 가능성
- 현재 secure=false는 폐쇄망 가정상 이해 가능
- 다만 향후 내부 SSL 적용 가능 여부는 별도 검토 필요

## 10. 개발팀 전달용 핵심 처방 요약

### 10.1 무엇이 가장 문제인가
- 기능 부족이 아니라 자산 기준정보 정합성 관리 체계가 아직 약함
- 데이터 실측 결과도 IP/OS 누락이 가장 큰 문제로 나타남
- AX 확장 설계는 문서에 있으나 운영문제로 연결되지 않음

### 10.2 무엇부터 해야 하는가
1. 정리 대상 규칙을 먼저 정의할 것
2. 그 규칙을 자산관리/대시보드에 노출할 것
3. 반입반출/계약/유지보수와 자산 상태의 불일치를 자동 점검할 것
4. 보안/권한/백업/감사 항목을 운영점검표 수준으로 구체화할 것
5. AX는 사진분석보다 정합성 자동점검부터 시작할 것

### 10.3 구현 난이도 대비 효과가 큰 영역
- 정리 큐 정의
- 데이터 품질 규칙 명문화
- 대시보드 정리대상 중심 전환
- 세션/키/백업 정책 점검
- 권한 매트릭스 문서화

## 11. 최종 결론
현재 솔루션은 방향성 자체는 맞다.
특히 "기능 확장형 시스템"보다 "자산 정합성 중심 운영형 시스템"으로 가야 한다는 진단은 타당하다.

다만 점검 관점에서 보면, 향후 보완은 다음 순서로 정리되어야 한다.

1. 증거 기반 정합성 규칙 정의
2. 그 규칙의 화면화(정리 큐/대시보드/자산관리)
3. 권한/세션/감사/백업 등 공공 운영거버넌스 구체화
4. AX를 정합성 자동화 중심으로 접목

최종적으로 본 시스템은 다음 상태로 정의할 수 있다.

> 현재는 기능적으로 충분한 자산관리 솔루션이며,
> 실사용 운영형 ITAM/CMDB 도구로 가기 위해서는
> 자산 정합성 규칙, 운영 거버넌스, AX 자동화 축을 더 명확히 구조화해야 한다.
